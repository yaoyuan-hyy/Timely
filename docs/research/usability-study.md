# Timely 首轮用户测试方案

状态：准备完成，尚未招募或执行。不能引用本文作为用户研究结果。

## 目的与招募

找 3–5 位已有记账或日程记录习惯的人，每人约 25 分钟。优先包含习惯手动表单、习惯聊天式输入的不同使用者。记录其原有工具与频率；熟悉项目的人单独标注。小样本用于发现问题，不估计总体准确率。

邀请文案（由项目作者自行发送）：

> 我在做一个自然语言记录原型，想观察你如何记一笔账或一件事。测试约25分钟，只用虚构数据，不需要填写真实账单或个人安排。不是测试你的能力，产品不顺手的地方正是我想了解的。你愿意试用并给反馈吗？

不默认录音录像；需要时单独征得同意。用 P01 等编号记录，不在公开仓库保存参与者姓名和原始联系方式。

## 环境与主持

每位参与者使用独立浏览器资料/存储环境，检查模型配置可用。说明“这是原型，请用合成场景；你随时可以停止”。主持人不教具体按钮、不暗示确认步骤；先观察自然尝试，超过两分钟或主动求助再提供最小帮助，并记录介入。

先问：平时记什么、用什么、最近一次忘记记录或记错是什么情况？属于访谈背景，不引导用户肯定自然语言方式。

## 任务卡（只读任务，不展示标准输入）

| 任务 | 交给参与者的情境 | 观察目标与完成标准 |
| --- | --- | --- |
| T1 记账 | 昨天午饭花了35元，留下这笔记录 | 最终流水日期为昨天、支出35元；观察是否理解确认 |
| T2 纠正 | 先输入一条午饭35元的草稿；保存前发现是45元，请纠正并保存 | 最终仅一笔45元；观察会否另建一笔 |
| T3 日程补充 | 想记录明天开会，先不写时间，等系统回应后补充下午3点 | 日期、时间、事项正确；追问是否易懂 |
| T4 查回 | 找到刚才记的午饭，说明日期、金额以及哪里能改 | 能找到正确记录并理解结果，不以固定输入匹配为成功 |
| T5 错误恢复 | 输入“6月31日上午10点开会”，随后改成6月30日 | 不保存非法日期，纠正后能确认正确记录 |

额外对照：用 Timely 的手动表单完成等复杂度的记账/日程任务。半数先自然语言，半数先表单，使用不同金额与事项避免记忆效应；注明样本小。不要拿没有实测的“传统工具时间”作比较。

## 测量与判定

- 无帮助完成：最终记录/查询正确、未获主持提示。另报有帮助完成与失败，分母为实际尝试任务数。
- 保存错误：最终保存的日期、事项、金额或条数错误；另计用户发现的预览错误。
- 完成时间：从读完任务并开始操作到最终正确结果；失败/超时单列，不只统计成功的快任务。
- 纠正轮数、系统追问次数、主持介入次数、网络等待和 API 故障分别记录。
- 每任务后问“完成这个任务有多容易？”1–7 分；最后问哪里不放心、哪些场景会用或不用，保留原意。

## 如何决定下一步

任何错误写入先复现并判断严重性；多人误认预览已保存，优先改状态与确认反馈；多人无法纠正，优先调整上下文/交互；完成可靠但明显比表单慢，再评估确认成本。此为预先定义的分析方向，不承诺基于 3–5 人得出显著性结论。

使用[记录模板](session-template.md)，结束后将匿名问题按频率、影响、可复现证据整理。结果报告必须写清测试版本、设备、人数、任务分母和辅助情况，再提出下一轮假设。
