# 流水分类契约 v1

分类单一来源是 `lib/ledger-categories.ts`，同时供模型提示、Zod 枚举、手动选择和 Repository 分类比较使用。

为兼容现有备份和浏览器记录，当前模型协议与 `LedgerEntry.category` 仍使用固定中文名称，不新增必须持久化的 categoryId。名称经注册表映射为稳定 ID 后进行 v2 查询比较；以后改显示文案需要显式迁移，不能直接修改旧名称。

模型按注册表的用途说明选择名称，不能自由创造“午饭”“打车”等分类；具体事项从原文摘取到 `note`，`sourceText` 继续保存输入。未知或不在范围内用“未分类”。分类与金额等字段共同经过 schema 校验，不用 few-shot 样例表修补模型输出。

新写入的分类、方向必须兼容；只修改收支方向造成旧分类冲突时，草稿继续追问分类。手动新增和编辑使用同一组选择项。模型查询的分类也受相同枚举约束，但允许任何明确指定的收支过滤组合，查询可正常返回空结果，不能擅自删掉过滤条件。

## 历史兼容

- 有限的精确旧标签（如“午饭”“打车”）映射到标准 ID，供读取、展示、修改和查询使用；不是自然语言输入关键词解析器。
- v2 分类筛选不再用备注包含分类名称作为命中依据，避免“去餐饮公司”的交通费计入餐饮。
- 读取时不重写原记录，不影响 expectedBefore 并发检查。未知自定义历史分类仍保留，UI 可以查看并保持原值；v2 标准分类查询不猜测它属于哪类。
- 旧别名在显示标准名称时仍作为事项展示；手动编辑归一化分类时，若没有备注则保留旧别名作为备注。
- v1 查询和旧接口仍保留兼容行为。没有给 CalendarEvent 新增分类系统，本轮处理的是讨论中的流水收支分类。

验证：Write v2 新增标准分类拒绝、方向冲突、历史别名查询与备注误匹配回归；原七条真实多轮评测报告写入 `docs/evals/write-flow-v2-category-contract.json`，不修改历史 gold。

本次真实结果：严格 6/7，fallback 0。午饭对应餐饮的多轮样例通过；失败为非法日期后重述时的上下文契约错误，分类收敛不代表其他模型行为已完全稳定。全量测试、类型、lint 和生产构建通过。
